# RF-16 — Autenticación y caducidad de cuentas

**Requisito (README):** Autenticación (usuario/contraseña) para todos los roles; fecha de
caducidad para todos excepto el administrador.

**Épica en `backlog.csv`:** "Autenticación Unificada, Control de Roles y Políticas de
Caducidad de Cuentas" (ID 16) — filas 356-372. 17 tareas: **2 Hecho, 3 Parcial, 12 Falta.**

## Estado funcional (independiente del backlog)

El núcleo de autenticación está sólido: sesiones separadas por aplicación (`sitio_token` /
`token`), verificación de identidad siempre en servidor, y la caducidad **sí se comprueba
en cada login** (120.2, Hecho — confirmado, `auth.middleware.ts` relee estado/caducidad de
la fila en cada petición, no solo al entrar).

Lo que falta de verdad es la mitad "automática" del requisito: **no hay ningún proceso
periódico que desactive cuentas vencidas por sí solo** — hoy una cuenta vencida se rechaza
si intenta iniciar sesión, pero sigue figurando como activa hasta ese momento. El propio
backlog lo describe con precisión en 120.1: "esa revisión existe y responde que todo salió
bien sin haber hecho nada" — confirmado directamente:
`api-backend/src/use-cases/usuarios/revisar-caducidad.job.ts` es un stub (`return { success:
true }` sin ninguna lógica).

## Corrección heredada de RF-15

La tarea 111.4 de esta misma familia de requisitos (política de contraseña con longitud y
mezcla de caracteres) aparece marcada Falta en RF-15 pero está **Hecho** — ver
`auditoria-rf-pendientes/RF-15.md` para la evidencia. Como RF-16 también depende de "una
política de contraseña definida" (`3-seguridad-del-proyecto.md` §5, fila RF-16 ya la lista
como ✅), esta corrección aplica igual aquí.

## Confirmado como está en el backlog (sin corrección)

- **119.1-119.3 (exigir fecha de caducidad obligatoria salvo administrador)** — Falta,
  con responsable y fecha asignados en el propio backlog (agosto - samuel, 8/6-8/10). Hoy
  el campo `fecha_caducidad` admite `NULL` para cualquier rol, no solo para el
  administrador — es exactamente la corrección que pide 119.3 sobre el criterio 114.1
  original.

  ninguno)** — Falta para la parte de "revisión automática" (porque esa revisión no existe
  todavía), pero ya existe una protección relacionada para la vía manual: el commit
  `4cd5e7e fix(usuarios): exigir al menos un administrador activo, no solo superadmin`
  (23-ago). Vale la pena que quien tome esta tarea confirme si ese fix ya cubre el caso que
  pide 121.2, para no duplicar el control.
